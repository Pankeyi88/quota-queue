# 已有任务额度恢复与串并行调度改造计划

状态：用户已批准，实施中。本文是改造目标与验收依据，不代表当前版本已具备所有能力；每阶段需另附实际测试及未完成项。

## 1. 需求与范围

### 1.1 目标

把插件从“预约新任务队列”调整为“已有任务的额度恢复与执行顺序管理”。

- 只管理用户已有的任务，不创建新任务、新会话或新的初始任务消息。
- 每个任务的额度等待与恢复都发生在它自己的原会话中；额度恢复后，重新启动该任务的执行，继续处理未完成工作。
- 用户可以选择一个已有任务单独恢复，也可以把多个已有任务安排为串行或并行批次。
- 不需要新任务预约面板、预约表单或新会话输入区的“预约消息”按钮。
- 调度由 Host 持有，浏览器关闭不影响已经授权的等待与恢复；Host 重启后先对账再决定是否继续。

### 1.2 术语与本计划采用的解释

| 术语 | 定义 |
| --- | --- |
| 已有任务 | 已由宿主创建、具有原始用户请求和稳定会话身份的任务；空白新会话、插件自行生成的任务不在范围内 |
| 一个任务内 | 每次恢复仍属于同一个已有任务及原会话，不把失败任务复制到新会话 |
| 重新开始 | 额度恢复后重新启动原任务的执行；不是清空上下文、重新发送原始完整提示词或从第一步重跑 |
| 恢复票据 | 插件内部的等待和去重记录，不是新的用户任务，也不应在 UI 中显示为另一个任务 |
| 调度计划 | 对已选已有任务的执行顺序及并行批次的描述，不是新的模型任务 |

如果宿主没有独立 taskId，首版以 sessionId 为任务身份，并将一次被中断的任务执行代次作为恢复范围。同一会话最多有一个受插件管理的活动恢复范围；后续用户新请求不能自动继承旧任务的授权。

如果“重新开始”实际要求从头重跑整个任务，需要另行确认；本文不包含这种会重复外部副作用的行为。

## 2. 不做的事

- 不再提供标题、任务正文、工作区、模型等新任务录入表单。
- 不通过插件创建会话、发送新的初始任务、复制任务或转移到其他会话执行。
- 不主动重置额度、不切换账户或凭据、不遍历其他账户、不读取浏览器保存的密钥。
- 不改变原任务的模型、工作区、审批策略或产品配置来规避额度限制。
- 不绕过审批、不直接重放工具调用、不承诺外部副作用 exactly-once。
- 不因重置时间到达、余额为零、普通 429 或模糊报错就认定额度恢复或耗尽。
- 不接管已经由 Goal、always-retry 或其他调度器持有恢复权的执行。

## 3. 使用流程与界面

### 3.1 单任务恢复

1. 用户打开一个已有任务，在会话状态区选择“额度恢复后继续此任务”。默认关闭，必须显式开启。
2. 若任务已经因可确认的额度错误停止，读取已有失败证据并建立一条恢复票据；若任务仍在运行，则仅授权监听后续额度中断。
3. 显示等待原因、上次查询结果、下次检查时间，以及恢复被阻止的原因。
4. 只有额度真实复查允许、原执行已停止且恢复所有权成立时，Host 才在原会话中调用受支持的继续机制。
5. 恢复执行再次遇到额度不足时，更新同一恢复票据，不新增任务或重复票据。
6. 用户可以撤销自动恢复、暂停等待；原生“停止”仍由宿主处理，插件必须遵守其结果。

### 3.2 多个已有任务的顺序

保留轻量的“已有任务调度”视图，不保留新任务预约面板。只允许从宿主可验证的已有任务中选择任务加入调度计划，不接受任务正文输入。

采用“有序批次”表达串并行：

```text
批次 1：[任务 A]                 # A 单独执行
批次 2：[任务 B，任务 C]         # B、C 可并行
批次 3：[任务 D]                 # B、C 均成功后，D 才可执行
```

- 每个批次一个任务就是串行；同一批次多个任务就是并行。
- 用户可移动尚未开始的任务、调整批次，以及配置明确的并发上限；默认并发上限为 1。
- 并行资格不代表保证同时获得额度。共享额度范围的任务共用复查结果并遵守冷却，不轮流轰炸查询接口。
- “额度恢复”只解除额度门禁，不能绕过用户设置的批次顺序。
- 运行中的任务不能被移动来释放占用或打破顺序。
- 后续批次仅在前一批次全部成功时自动放行。失败、取消、用户停止、结果不明都不算成功。
- 如需绕过失败任务，用户必须明确选择“跳过此项并放行后续”；保留原结果与操作记录，不伪装成完成。
- 同一会话始终互斥。首版同一工作区默认互斥，不允许仅凭两个会话不同就并行修改同一目录；需要同工作区并行时另行设计隔离机制。
- 已经由宿主开始的执行不被插件强行停止或重排；若与新计划顺序冲突，计划进入“需要处理”，不声称已控制其启动顺序。

### 3.3 必要展示与操作

每项展示：任务标题、原会话入口、工作区、批次、状态、等待/阻止原因、最近一次恢复结果。

操作必须区分：

- 暂停整个计划：不再启动后续执行，不中断已运行任务。
- 暂停某项自动恢复：保留任务和票据，不再自动继续。
- 移出计划：撤销该计划对任务的管理，不删除原会话，不停止已经运行的任务。
- 立即检查额度：只读查询，有去重与退避，不直接强制执行。
- 跳过阻塞项：显式确认后放行后续批次。

缺少配置或执行能力时显示具体原因并禁用对应操作，不显示虚假的“即将自动恢复”。

## 4. Host 行为与安全约束

### 4.1 恢复必须同时满足的条件

1. 用户对当前任务执行范围的恢复授权仍有效。
2. 中断原因有可信的额度证据，身份可关联到原会话、失败步骤及执行代次。
3. 使用该任务原有、已固定绑定的凭据及模型路由查询额度。
4. 适用额度窗口经真实只读查询后均不再阻塞；认证失效或未知结果不放行。
5. 原执行已被宿主正向证明停止，不以租约超时或前端 idle 代替。
6. 宿主级排他恢复所有权已取得，且不存在其他恢复执行者。
7. 批次依赖、全局并发、会话互斥与工作区互斥允许启动。
8. 原工作区、模型和审批配置没有不兼容变化。
9. 恢复意图和执行关联先可靠持久化，再调用宿主。

任一条件无法证明时保留任务并进入等待或“需要处理”，不得自动执行。

### 4.2 状态与完成判定

建议状态：`armed`（已授权监听）、`waiting_quota`、`waiting_order`、`paused`、`resuming`、`running`、`succeeded`、`failed`、`needs_attention`、`removed`。额度状态与调度状态分别保存，UI 可同时显示多个阻止原因。

- 同一会话、失败步骤、执行代次的重复错误只能命中同一票据。
- 只有关联到本次恢复的 message/turn 以及宿主明确成功终态，才能记为 succeeded。
- 投递成功、请求返回、idle、流结束本身都不等于任务成功。
- 取消或停止不自动重新排队。用户手动继续后，后台票据必须消解或重新对账，不能双发。
- 恢复调用结果不明时保留执行占用，先对账，不能直接重试或放行下一任务。

### 4.3 持久化与重启

持久化计划版本、批次、任务身份、授权范围、额度范围、恢复票据、执行关联和排他占用；不持久化密钥或原始认证头。

Host 重启后恢复等待与顺序信息；遗留 resuming/running 必须对账。不能证明旧执行结束时进入 needs_attention 并保持必要占用。关闭浏览器不撤销已有授权，用户停止、撤销授权或任务身份变化则必须阻止后续恢复。

## 5. 对现有实现的改造

| 模块 | 改造内容 |
| --- | --- |
| Client | 删除新会话预约按钮、预约对话框及其注册；保留原任务状态区，重做为已有任务选择与批次排序视图 |
| Host RPC | 新增已有任务枚举/校验、加入计划、调整批次、授权/撤销、跳过、移出等受控操作；旧新任务新增/编辑入口退役 |
| Core | 复用额度归一化、持久化、恢复去重及执行占用保护；将全局固定串行改为批次依赖加有界并发 |
| Host 适配 | 接入真实额度只读查询、额度错误事件、原会话继续、成功终态对账及宿主排他恢复协议 |
| 数据迁移 | 旧手动预约任务不自动转为可执行已有任务；保留为只读历史并解释原因。迁移前备份、版本校验，失败不启动调度 |
| 发布与文档 | 更新接口契约、权限说明和验收记录；统一发布包来源，明确新旧功能边界 |

保留现有测试中仍适用的安全不变量。删除预约相关测试必须由“旧入口确实移除”和已有任务恢复测试替代，不能只通过减少测试数获得全绿。

## 6. 实施阶段与退出条件

### P0：宿主契约核实

确认已有任务身份与失败证据、只读额度认证、原会话继续接口、终态关联、排他所有权及审批继承。输出“可用/缺失/需宿主改造”的证据清单。

退出条件：能证明安全恢复链路；缺少契约时明确列出宿主适配工作，不能把待办仅描述为用户填配置。

### P1：单任务恢复闭环

先移除预约入口，完成单个已有任务的授权、额度等待、同会话继续、再次耗尽、手动停止与撤销处理。

退出条件：单任务离线回归和真实宿主受控验收通过；不创建会话、不重发初始任务、不双重执行。

### P2：已有任务串行

加入计划持久化、单任务批次、排序、暂停、跳过及重启对账。

退出条件：串行顺序与成功终态严格关联，等待额度或结果不明时后续任务不越序。

### P3：有界并行批次

在宿主所有权已验证的前提下增加批次内并发、并发上限、工作区互斥与共享额度退避。

退出条件：并发与额度竞争故障测试通过；真实受控执行证明既不越上限，也不提前放行下一批。

### P4：迁移与正式交付

完成旧数据兼容、正式安装、现有 GUI 验收、文档与安装包校验，记录真实通过和仍未验证的边界。

## 7. 验收方案

### 7.1 分层方法

- Core：离线状态机、假时钟、可控额度响应与并发 barrier，覆盖竞态和崩溃窗口。
- Host：真实 Cordis/RPC 加可控端口，验证认证、持久化、生命周期及宿主适配；模拟结果不算真实恢复通过。
- GUI：在现有 Harness URL 用正式插件验收，不用独立演示页替代。
- 端到端：经用户批准的专用已有任务、固定凭据和无破坏性工作负载。先用受控故障验证链路，再以真实额度阻塞与恢复样本验收；二者分开记录，不为制造耗尽大量消耗额度。

### 7.2 必测清单

| ID | 场景 | 通过标准 |
| --- | --- | --- |
| U01 | 移除新任务预约 | 新会话无预约按钮，无任务正文录入表单；宿主原生模型/发送控件不受影响 |
| U02 | 选择已有任务 | 仅接受宿主验证的已有任务；拒绝空白会话、伪造 ID 和重复加入 |
| R01 | 单任务耗尽后恢复 | 授权后遇可信额度错误，建立一条票据；恢复后仍在原任务、原会话执行 |
| R02 | 不从头重跑 | 不新建会话、不重发初始完整请求、不直接重放已经完成的工具；恢复前后的执行关联可追踪 |
| R03 | 到期但额度未恢复 | 到期只触发复查；查询仍阻塞、失败或未知时不调用继续 |
| R04 | 错误分类 | 401/403进入认证处理；普通429不误建额度票据；余额零及取整100不单独判断耗尽 |
| R05 | 多窗口限制 | 所有适用阻塞窗口均解除才允许恢复 |
| R06 | 重复事件与再次耗尽 | 重复错误只留一票据；恢复后再次耗尽更新原记录，没有第二个用户任务 |
| R07 | 用户停止/撤销 | 用户停止、撤销授权或手动继续后，插件不在后台重复启动 |
| R08 | 配置或所有权不足 | 任一恢复条件缺失均禁执行，界面解释具体原因 |
| S01 | 串行 A→B | A等待额度、运行或结果不明时B不启动；A明确成功后B才取得资格 |
| S02 | 批次 [A,B]→[C] | A/B可按上限并行；必须二者均成功后C才能启动 |
| S03 | 并发与互斥 | 原子 claim 保证不超全局上限；同会话及同工作区不出现重叠执行 |
| S04 | 额度与顺序独立 | B先恢复额度但A未结束时，B仍等待顺序，不抢跑 |
| S05 | 失败与跳过 | 失败/取消不自动放行后续；显式跳过有确认、持久化记录且不篡改原结果 |
| S06 | 调整顺序 | 仅未运行项可移动；与调度并发时以提交后的持久计划为准，不出现旧顺序执行 |
| S07 | 共享额度 | 同一范围并发到期仅一次查询；共享冷却，无查询风暴或账户切换 |
| S08 | 宿主外部启动 | 用户或其他执行者抢先启动时，插件对账并阻止冲突，不强行接管 |
| P01 | 持久化失败 | 保存失败不得提示已安排，也不得发起恢复或放行下一批 |
| P02 | 关闭浏览器 | 已授权计划仍由Host等待与调度，重新打开后状态一致 |
| P03 | 重启与崩溃 | queued/waiting顺序保留；运行与投递不明先对账，不能凭租约超时启动第二执行者 |
| P04 | 双执行者竞争 | 两个潜在恢复执行者只能一个取得宿主所有权；另一方明确退让 |
| P05 | 旧数据迁移 | 旧预约任务不自动执行，不丢失；损坏/未知版本数据使调度安全停止 |
| G01 | 完成证据 | RPC投递、idle及流结束均不单独放行；匹配的成功终态才推动批次 |
| G02 | UI反馈与键盘 | pending防重复，失败不假更新；深浅主题、焦点及键盘操作通过 |
| G03 | 插件生命周期 | 禁用/启用清理监听与定时器，不留双调度器；禁用不擅自停止宿主任务 |
| G04 | 安全边界 | 无密钥泄露、无额外凭据查询、无主动重置、无审批绕过，沿用原任务配置 |

### 7.3 必须留存的验收证据

每项记录版本、环境、步骤、预期、实际结果以及状态：未测 / 离线通过 / 宿主受控通过 / 真实额度通过 / 失败。

关键证据包括：

- 单任务恢复前后相同的任务及会话身份、唯一恢复票据、关联执行终态。
- 串行/并行执行时间线、claim与release记录，以及可核对的并发上限。
- 查询结果的去敏状态与放行原因；不保留密钥、token、原始认证头。
- 浏览器关闭和Host重启后计划一致性及对账结果。
- 正式安装包版本、SHA-256、运行时版本与完整测试报告。

## 8. 完成定义

只有同时满足以下条件，才宣称本次改造完成：

1. 新任务预约入口与能力已退役，用户只能选择已有任务进行恢复和排序。
2. 单个已有任务在真实额度阻塞解除后能在原会话继续，且不重复启动或从头重跑。
3. 多个已有任务的串行、有界并行批次及失败阻塞规则按计划生效。
4. 用户停止、撤销授权、手动继续、浏览器关闭、Host重启及模糊投递均有通过证据。
5. 真实额度查询、宿主恢复所有权与终态对账均已接通；仅有mock测试或UI截图不算完成。
6. 所有适用回归测试通过，未验证项明确列出；缺少安全契约时继续保持执行禁用。

建议先验收“一个已有任务的额度恢复闭环”，再扩展串行，最后增加并行。并行支持不能作为跳过宿主排他协议的理由。
